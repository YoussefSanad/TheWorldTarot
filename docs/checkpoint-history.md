## How Bunny playback actually works

The part that cost five days. Anything here that looks arbitrary is load-bearing, and getting any one of them wrong produces an identical 403 with nothing to distinguish it.

- **The token is scoped to the video's directory, not to the manifest.** HLS resolves renditions and segments relative to `playlist.m3u8`, so a file-scoped token loads the manifest and 403s on everything it points at. From `curl` that is indistinguishable from working
- **The viewer's IP is not in the hash, and putting it there cannot work.** It was there from 3 to 7 August 2026 and never worked once. The API is behind a dual-stack Cloudflare and `vz-9f79c10d-ea5.b-cdn.net` has no AAAA record, so a visitor with IPv6 got a token signed for their v6 address and then reached the zone over v4. Bunny hashed the address it saw, disagreed, and refused. `App\Support\ViewerIp` was deleted with it. **Proved by a control on 7 August**: draw over v6 then fetch over v4 gives 403, draw over v4 then fetch over v4 gives 200, everything else held equal
- **`token_path` appears twice, encoded differently.** Raw inside the hash, percent-encoded in the query
- **A playback URL cannot be opened in a browser tab.** The zone refuses requests with no referrer, so these only work from inside a page. Nobody, support included, can debug one by clicking it
- **The zone's security key and the library's token key are the same value with two names**, on two different dashboard screens. Five rounds were lost to that collision
- ~~**The frontend must fetch a playback URL from the browser, never from a server.**~~ **Corrected 7 August 2026, and it is the same correction as the bullet above.** That rule existed only because the token bound to an address, and it went with the binding. **A server-side fetch is fine.** Caching the result is still wrong, because a playback URL is a credential with a timer

## Traps already paid for

Do not rediscover these.

- **`config('app.locale')` is written by `app()->setLocale()`.** Use `config('app.fallback_locale')` for the default language. Reading the wrong one switched the entire completeness gate off for non-English requests
- **Route parameters bind in path order, not by name.** A content action takes `(string $locale, string $key)`. Omitting the first silently receives `en` as the key
- **Filament plugin locale lists are captured when the panel registers.** Resources override `getTranslatableLocales()` so the list is read when the form is built
- **Migrations must not reference enums, config keys or support classes**, only literals. Three migrations had to be rewritten when the things they referenced were renamed or deleted
- **A translatable attribute reads as `''`, not `null`, when a translation is missing**, and assigning `null` stores `{"en": null}`
- **A factory state that builds translations from other attributes is order-dependent.** `translatedInto('es')->create(['name' => ...])` translated the default name and then had the column overwritten, producing a card that claimed to be translated and was not. Applied to the made model instead
- **Filament's `unique` rule counts soft deleted rows**, so a panel can refuse a value the database would accept. Cards carry a partial unique index and the form rule matches it
- **`pluck()` on a translatable column returns raw json**, not the array the model would give you
- **A file field on a translation tab is emptied by the language switcher**, and saving that translation then deletes the file. The card picture is scoped to the original language for this reason. Ordinary fields are unaffected, product prices included, which is what made it look like a card-only problem at first
- **Laravel Cloud publishes attached buckets as one JSON blob**, `LARAVEL_CLOUD_DISK_CONFIG`, naming the disk each replaces. It sets no `AWS_BUCKET`, and credentials arrive through the container credential provider rather than as keys. A day was lost hunting for variables that were never going to exist
- **The queue runs inline in tests**, so anything that dispatches on save reaches a third party during setup. Tests about the moment of upload have to hold the queue
- **`Http::assertSent` cannot read a body from a stream the code has already closed**, which is correct behaviour on both sides. Assert the bytes where nothing closes the stream
- **`expectsOutputToContain` consumes the line it matches**, so two expectations against one line silently fail the second
- ~~**The platform's scheduler must tick every minute.**~~ **Measured 26 August 2026 and the answer is worse than this bullet assumed: it ticks every five minutes.** The correction that matters is not the number. `Event::isDue` compares a task's cron expression to the exact minute the platform invoked `schedule:run`, so an unaligned five minute cadence never fires `*/5` and never fires `0 0 * * *` at all, rather than firing them late. **Frequency lives in code and alignment lives on the platform, and only the pair says what actually runs.** Closed by Youssef, who has the platform's own answer. Production is a separate measurement and has not been started
- **A proof has to travel the channel real users travel.** `curl` defaults to IPv4. Staging playback was proved that way on 3 August 2026 and was broken for every IPv6 visitor from that moment until 7 August, which is most home broadband and effectively all mobile. This is the M4 lesson wearing different clothes: it is not enough for the assertion to come from the other side, the request has to arrive the way a real one does
- **A test that asserts an external service's format against your own implementation of it proves nothing.** This is the trap that cost the most. It is not a weak assertion, it is an assertion about the wrong thing, and it stays green through total failure. Anything only the other side can confirm needs a vector captured from the other side and pinned. `BunnyStreamTest` now does exactly that
- **Bunny's embed player plays with no token at all** when embed token authentication is off. **It is on since 16 August 2026 and the door is shut**, but the lesson it leaves outlives the setting: a film playing in a browser was never evidence that signing works, because a second surface was serving it unsigned the whole time, and that is probably what let M4 close on a false claim. **A service can have more than one door, and proving one is locked says nothing about the others**
- **A skipped test reads as a passing one in the summary line.** `it answers 404 for a card with nothing to watch` was written into the staging walk on 13 August 2026 and asserted something the design must never do. Nobody knew for ten days, because staging had no card with a film, so it skipped every run and the totals looked clean. It failed the first time it ever executed, on 23 August. The walk's own README already says to read a skip as a skip; this is that warning collecting. **Count the skips, and know which ones are new**
- **A test can encode the exact opposite of a security property and look reasonable.** That same test asked for 404 on a card with no film, using the account the file elsewhere relies on having no pass. Granting it would have meant 403 for a card with no film and 404 for one that has it, which is an oracle: anybody with a free account could walk the ids and learn precisely which films exist. The gate is asked before the card is looked up for that reason, and it has been since `d23fe09`. **When a test and a documented security decision disagree, find out which is older before touching either**
- **A `git worktree` sharing a symlinked `vendor` runs the wrong code.** Composer's autoloader stores an absolute `$baseDir`, resolved from where `vendor` really lives, so `App\` still points at the main checkout. Comparing two commits that way on 23 August 2026 produced a byte-identical OpenAPI diff that meant nothing, because both exports had run the same code. It surfaced only because the "before" document mentioned a class that did not exist at that commit. **Copy `vendor` and re-dump the autoloader in the worktree, and give any before/after comparison a sanity check that proves the two sides differ.** A clean diff is exactly what a broken comparison looks like
- **Bunny's error pages answer HTTP 200 with the failure in the body.** The refused embed page comes back `200 OK`, 2841 bytes, with `<title>403</title>` inside it. Checking the status code alone, which is the obvious way to test this, reports the door still open when it is shut, and would report it shut if it were open the day the page changes. Read the body
- **A Filament file field does not delete the file it removes.** `deleteUploadedFileUsing` is null by default, so clearing the field clears the path and leaves the object in the bucket. Every replaced master leaked one until 7 August 2026
- **A queued cleanup job must carry strings, never the model.** By the time it runs the row has forgotten what it used to point at, so a job holding a `Card` reloads it and finds nothing to delete. What is being deleted is captured at the moment of the save
- **A 404 from a delete is success, not failure.** The queue delivers at least once, so the second run finds the thing already gone. Treating that as a failure fails every redelivery and parks a job describing work that succeeded
- **An `HttpException` with no message renders as `{"message": ""}`** once debug is off, which reads like a routing mistake and is not one. An afternoon went on that on staging on 7 August 2026. Give a 404 a reason if there is more than one way to reach it
- **Two different Bunny secrets are both called "Token Authentication Key"**, on the Stream library screen and the pull zone screen. They hold the same value here, which made six rounds of "you sent the wrong key" all wrong
- **A blank environment variable is not an absent one, and `env()`'s default only covers absent.** `MAIL_FULFILLMENT_RECIPIENT=` with nothing after it returns `''`, not the fallback, and `.env.example` shipped it exactly like that while `composer setup` copies that template into place. The address Jennifer's "somebody is waiting for a reading" notification goes to resolved to an empty string everywhere the template had been used, and the send reported success. Fixed 13 August 2026 by falling back with `?:` throughout `config/mail.php`. **Assume any hosting panel field can be blank rather than unset**, because a cleared field produces the same thing.

  **It collected again on 26 August 2026, in phase B, and the second time it was money.** `config/payments.php` decided whether to offer Stripe with `env('STRIPE_SECRET') === null`, and `.env.example` ships that key present and empty, so the check said "configured" on every laptop that had run `composer setup`. The file's own comment promised the opposite in the lines directly above it. Found by review rather than by anything failing, because nothing fails: the method is offered, resolves, and dies on its first call to Stripe, which is the worst moment a shop has. **`blank()` rather than `=== null`, everywhere a credential decides whether a feature exists.** The comment being right while the code was wrong is the part worth remembering, since a comment cannot be tested and reads as evidence anyway
- **The `log` mailer accepts every message, reports success and delivers nothing.** An environment left on it looks healthy from the inside and is silently discarding password resets. `php artisan mail:check` exists for this, and says so out loud when the mailer is `log`. Run it with `--now` as well as without: `--now` tests the transport, the default tests the transport and the queue worker together, and those two failures look identical from the outside
- **A nullable password column is the kind of thing that quietly makes an authentication check pass.** `Hash::check` against null returns false, so the explicit null check in `SessionController` changed no test when it was removed on 9 August 2026 and was put back anyway: that behaviour is the framework's guarantee rather than ours, and the next person to authenticate a customer may not route through there. What actually keeps an unclaimed account shut is a test that tries every route into one
- **Rate limiting a sign in has to answer 429, not 422.** Laravel's own starter kits raise a validation error there, which renders as 422 on the email field. `API_CONTRACT.md` section 7 promises the partner that being rate limited is a 429 with `Retry-After`, and a second way of saying it is a way for their retry logic to miss it
- **An inline `throttle:n,1` with no prefix shares one counter per address with every other one in the application.** Laravel keys a guest's limiter on the domain and the IP, never on the route, so the strictest limit in `routes/api.php` applies to the sum of every throttled route a visitor touches, and a signed in customer keyed on their id shares a bucket the same way. Six requests to `/api/v1/orders` refused the next `/api/v1/forgot-password` on its first call, so buying something spent the budget for remembering your password. Found on staging on 13 August 2026 by `tests/Staging`, and invisible to the feature suite because each test there makes one or two requests against a fresh cache. **Fixed the same day** by giving every throttle its own prefix, the middleware's third argument, and pinned by `it does not spend the reset budget on unrelated endpoints` in `PasswordResetTest`. That test was checked against the unfixed routes first, because a regression test that passes on the broken code proves nothing
- **A platform helper can turn an address into user input, and your code will not show it.** `Illuminate\Http\Middleware\TrustProxies` applies `'*'` by itself when nothing is configured and `laravel_cloud()` is true, and trusting everything makes Symfony return the **leftmost** entry of `X-Forwarded-For`, which is whatever the client wrote there. So `$request->ip()` was caller supplied in both deployed environments until 15 August 2026, and `LoginRequest`'s per-account limiter could be stepped around with a header rather than merely being coarse. **The first fix was also wrong** and made the address a constant instead, which would have shared one rate limit bucket across the entire internet. Neither state was visible from the test suite, because a synthetic request chain proves what you built and not what the balancer sends. **The residual is still open**: the peer is trusted unconditionally, so anything reaching the balancer without passing through Cloudflare, on the `*.laravel.cloud` hostname, is trusted one hop too far
- **Mailchimp will not re-add a permanently deleted address, ever, through any API call.** Found by walking, and pinned as a vector in `MailchimpVectorTest`. **Archive test contacts, never permanently delete them**, because a permanent delete burns that address for good and `yosefsanad11@gmail.com` is the one that found out. Related and separate: an identical second POST answers 400 Member Exists, which this system handles as success, since somebody signing up twice has not done anything wrong
- **A test that reads its expectation out of an env file is a test of that machine.** `NewsletterListTest` resolved the default newsletter driver and expected the logged list, which held only because one developer's `.env` carried `NEWSLETTER_DRIVER=log`. CI copies `.env.example`, where that line is commented out, so config fell through to Mailchimp exactly as designed and the suite failed on the first pull request that ran it, 16 August 2026, on staging into main. **The config was right and was not touched**: an absent or unrecognised driver gets Mailchimp on purpose, so a typo cannot quietly stop collecting subscribers. The test now names the class it expects, and `phpunit.xml` pins `NEWSLETTER_DRIVER=log` as well, which matters for a second reason: the queue runs inline in tests, so an unpinned driver plus a real key in somebody's `.env` puts test signups in Jennifer's launch audience. **This is the `.env.example` trap below wearing different clothes**, and the general form is that anything `composer setup` or CI copies is a second environment nobody is looking at
- **Pest reads a name that is not a class as an expected message**, so `not->toThrow(SomeInterface::class)` passes while asserting nothing at all. It looks like a passing test about an interface and is a passing test about a string
- **Two implementations of one rule, kept in agreement by hand, fail silently rather than loudly.** A query and a predicate answered "is this card on the website" separately, and because they serve different callers, their disagreeing was never a failing test. It was a card in the Library that said it was watchable and 404d when watched. **The tell is that nothing is red**, so the only defence is stating the rule once and rendering it, which is what `App\Availability` does and what `availability:check` proves on real rows
- **A missing column is loud in SQL and silent in PHP, and the silent half is worse.** A currency configured with no price column killed the product listing with a Postgres error, and in the predicate read as null, became zero, and answered that nothing was priced. **The same mistake broke the shop or emptied it depending which caller asked first**, and the empty version looks exactly like an empty database. Both raise `UnpriceableCurrency` now
- **A test suite staying green while you delete a condition means the condition was never tested.** The language check was removed from the product declaration entirely and all 715 tests passed. Cards had carried that test since M3 and products never had it, so a reading could have leaked onto the Spanish site untranslated and nothing would have said so. **Deleting a rule to see whether anything notices is a cheap way to find out what your suite actually covers**
- **Mail queued inside a transaction that then rolls back has still been sent.** Nothing unsends it. In `MarkOrderPaid` the access grant is inside the transaction, so a half-failure cannot leave somebody holding a pass for an order that never went paid, and every message is queued after the commit. The two rules pull in opposite directions on purpose
